while loops · Why

Keep going until it's done

A for loop is for when you know how many times to go round: once per note in the melody.
A while loop is for when you don't know in advance. You only know when to stop.
For example: keep rolling until you get a six, keep adding notes until the melody is 4 seconds long, or keep asking until the input is valid.
Ask first: "When do you know in advance how many times something will happen, and when don't you?" Take two or three answers. The dice example works well acted out: one student rolls and says the number aloud, the room calls "again" until it's a six. Nobody could have said beforehand how many rolls it would take. That's a while loop.
while loops · How
What you already know
// we know how many: 8 notes
let notes = [];

for (let i = 0; i < 8; i++) {
  notes.push("C4");
}
The new way
// we only know when to stop
let time = 0;
let notes = [];

while (time < 4) {
  notes.push("C4");
  time = time + 0.5;
}

Check the condition, run the body, then check again. If nothing in the body changes the condition, the loop never ends.

Read the while loop aloud with the room: "while time is less than 4, add a note, add half a second, go back and check." Have one student hold the value of time and update it out loud each pass. Count the passes together: 8, the same as the for loop. Common mistake: forgetting to change time in the body, which freezes the tab. Delete that line live and ask what would happen (don't run it).
break and continue · Why

Leave early, or skip a turn

Sometimes you find what you're looking for halfway through the line, and there's no point walking the rest.
break leaves the loop straight away.
continue skips the rest of this pass and goes on to the next item, for example to skip rests or empty steps in a pattern.
Act it out: line up five or six students, each holding a card with a note name, one "rest" and one "STOP". One person walks the line and sings each note. At "rest" they step past without singing (continue). At "STOP" they walk away from the line (break). Ask: what happened to the people after STOP?
break and continue · How
What you already know
let stopped = false;

for (let i = 0; i < melody.length; i++) {
  if (melody[i] === "STOP") {
    stopped = true;
  }
  if (!stopped && melody[i] !== "rest") {
    synth.triggerAttackRelease(melody[i], "8n");
  }
}
The new way
for (let i = 0; i < melody.length; i++) {
  if (melody[i] === "rest") {
    continue;   // skip this one
  }
  if (melody[i] === "STOP") {
    break;      // leave the loop
  }
  synth.triggerAttackRelease(melody[i], "8n");
}

Same result, but the new version stops walking the line at STOP, and you don't need an extra variable to remember that you've stopped.

Point out the left version still visits every item after STOP; it only skips playing them. Ask the room which version reads more clearly aloud. Common mistake: putting continue or break outside a loop, which gives a SyntaxError. Another: putting the play line before the checks, so the rest still plays.
Anonymous and arrow functions · Why

Functions without a name

Some functions are only used once, in one place, and handed straight to something else. Giving them a name only adds noise.
An anonymous function is a function with no name. An arrow function is a shorter way of writing one.
You'll see them all over modern JavaScript, especially with event listeners and array methods.
Link back to the Functions lecture: a function is a named process. Today's twist is that the name is optional when you only use it once. Students will meet arrow functions in almost every example online and from AI tools, so the point is mainly to read them, not to switch everything over.
Anonymous and arrow functions · How
What you already know
function double(n) {
  return n * 2;
}

double(4); // 8
The new way
// anonymous function in a variable
const double = function (n) {
  return n * 2;
};

// arrow function
const double = (n) => {
  return n * 2;
};

// one expression: drop braces and return
const double = n => n * 2;

All of these do the same job; pick one, you can't declare double three times in real code. The arrow version is the one you'll read most in other people's code.

Morph the left version into each right version step by step: take the name off and store the function in a variable; swap the word function for an arrow; drop the braces and return. Read the last one aloud: "double is: take n, give back n times 2." Common mistake: keeping the braces but dropping return, which gives undefined.
Callbacks · Why

Hand over a function for later

A callback is a function you pass to another function, so it can call it at the right moment.
You already do this! addEventListener takes a function and calls it when the key is pressed.
Arrays have methods that take callbacks too: forEach runs your function once for every item, with no counter to get off by one.
Act it out: one student is the browser and another is playC. Hand the browser a role card that says "play C4". The browser waits. When someone claps (the click), the browser reads the card and plays the note. The function was handed over, and the browser decided when to call it.
Callbacks · How
What you already know
function playC() {
  synth.triggerAttackRelease("C4", "8n");
}
button.addEventListener("click", playC);

for (let i = 0; i < melody.length; i++) {
  synth.triggerAttackRelease(
    melody[i], "8n", Tone.now() + i * 0.4);
}
The new way
button.addEventListener("click", () => {
  synth.triggerAttackRelease("C4", "8n");
});

melody.forEach((note, i) => {
  synth.triggerAttackRelease(
    note, "8n", Tone.now() + i * 0.4);
});

playC was already a callback. Notice there are no brackets after it: you hand the function over, and the browser calls it later.

The most common bug here, and one that turns up in A1 code: writing playC() inside addEventListener. That calls it immediately and hands over its result (undefined). Show that version and ask what would happen. For forEach, point out that the callback gets the item and its position, so there's no i to manage.
map and filter (bonus) · Why

Make a new array from an old one

Very often, a loop does nothing but build a new array: every note transposed, or only the loud notes kept.
map transforms every item and gives back a new array of the same length.
filter keeps only the items where your callback returns true.
Bonus: skip this pair if time is short. Act out map: a row of students each holding a volume number; one student is the callback and multiplies each by 100, writing the answer on a new card. Filter: the callback says yes or no, and only the yes cards move to the new row.
map and filter (bonus) · How
What you already know
let percent = [];
for (let i = 0; i < volumes.length; i++) {
  percent.push(volumes[i] * 100);
}

let loud = [];
for (let i = 0; i < volumes.length; i++) {
  if (volumes[i] > 0.6) {
    loud.push(volumes[i]);
  }
}
The new way
let volumes = [0.2, 0.9, 0.5, 1.0];

// map: transform every item
let percent = volumes.map(v => v * 100);
// [20, 90, 50, 100]

// filter: keep only some items
let loud = volumes.filter(v => v > 0.6);
// [0.9, 1.0]

Neither one changes the original array. Each gives you back a new array.

Ask the room to predict the results before revealing the comments. Common mistake: forgetting that map's callback must return a value. With braces and no return, you get an array full of undefined. Note that 1.0 shows as 1 in the console.
The ternary operator · Why

A choice in one line

Often an if/else exists only to pick between two values.
The ternary operator, condition ? a : b, picks the value in a single expression.
It's handy when setting a variable, or a label or colour on the page.
Ask for examples from their A1 projects where an if/else only picks a label, colour or sound. A play/stop button is the classic one. Keep it short: it's a reading skill more than a writing one.
The ternary operator · How
What you already know
let label;

if (isPlaying) {
  label = "Stop";
} else {
  label = "Play";
}

button.textContent = label;
The new way
let label = isPlaying ? "Stop" : "Play";

button.textContent = label;

// or straight into the page
button.textContent = isPlaying ? "Stop" : "Play";

Read it aloud: "is it playing? then Stop, otherwise Play." If it doesn't fit comfortably on one line, go back to if/else.

Have the whole room read the line aloud as a question and answer. Warn against nesting ternaries: technically allowed, almost always harder to read than if/else. This ties back to the code review theme: the clearest version wins.
