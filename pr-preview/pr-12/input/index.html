Input and response · Why it matters

  
This is what we design

  
An event is anything that happens: a person presses a key, a timer runs out, a message arrives. Interaction design decides how a system responds. Three questions to argue about:

  

    
Mapping
Which event should cause which response? Why that one?

    
Feedback
How does the person know something happened?

    
Timing
How fast is fast enough? When does slow feel broken?

  

  
Pick one thing you set in motion today. Ask all three questions about it.

  
Open these up rather than settling them. Events don't only come from people: a phone buzzes because a message arrived, a screen dims because a timer ran out. Today's events come from the keyboard, but the same idea covers all of them. Mapping: why is the volume knob turned clockwise for louder? Which key should play the lowest note? Feedback: the click of a key, the light on a button, the sound itself. Timing: around a tenth of a second feels instant; for an instrument even less. Come back to all three in the last part of the lecture, when they choose their own key mappings.

Events and listeners

  
Events happen. Who is listening?

  

    

      
01The browser calls out every event as it happens: "keydown, a!" "keyup, a!" "click!" It never stops, and it doesn't check who is listening.

      
02Three functions each know one job. playNote sings the note for the key, stopNote stops singing, showKey says the key out loud. They only act when called.

      
03The programmer connects an event to a function by writing it on the board: keydown → playNote. That line is a listener.

      
04When an event fires, the browser hands an event card (its type and key) to every function connected to it.

    

    

      
four rounds

        
    
          
  1. Nothing connected. The browser fires events.
    2. 
          
  2. Connect keydown → playNote.
    3. 
          
  3. Hold a note, fire keyup. Then connect keyup → stopNote.
    4. 
          
  4. Connect keyDown → showKey. Fire away.
    5. 
        

      

      
Afterwards: who fires the events, who connects them, and who calls the function?

    

  

  
About seven minutes, before any syntax. Before class: write keydown, keyup and click as three column headings on the whiteboard, and have some blank cards for event cards. Volunteers: one browser, three functions (give each a card with their name and job), one programmer at the board. Round 1: the board is empty; the browser fires a stream of events ("keydown, a!" "keyup, a!" "click!"). Nothing happens. Ask: did the events happen? (Yes. Every one. Nobody was connected to them.) Round 2: the programmer writes playNote under keydown. Now each keydown means the browser writes the key on a card and hands it to playNote, who sings. keyup and click still go nowhere. Round 3: playNote starts a note on keydown and keeps singing; nothing stops it until stopNote is connected to keyup. Round 4: the programmer writes showKey under a new heading, keyDown. The browser never fires an event called that, so showKey never gets called, and nobody gets an error. Optional: connect showKey to click too. The browser hands it a card with no key on it, so it says "undefined". Debrief: the browser fires events all the time, whether anyone listens or not. addEventListener is the programmer writing a line on the board. The browser calls the function, and hands it the event.

The strip at the bottom follows the value: what the last line hands to twice, what the parameter action holds, and what happens each time twice calls action(). With twice(clap), action holds the function, and twice decides when to call it: twice. twice doesn't know or care that it's clapping; hand it stomp and it stomps. When you hand a function over, whoever holds it decides when to call it, and what to give it. That's why playNote has an event parameter: the browser fills it in.

  
The payoff. Three ways the same kind of function gets called. Run the line: one call, now, and you chose when. Start Tone: calls every beat until you stop it, and you didn't write any of those calls. Press keys in the pad: a call for each key, and the person at the keyboard chose when. Discuss: why hand a function over instead of calling it? Because you don't know when it should run (the person decides, or the beat, or a timer), and because the caller has information you don't have yet: the time of the beat, which key was pressed. That's what the parameters are for.
