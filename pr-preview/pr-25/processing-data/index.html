From the world to data

A program can't hold a person tapping.

It can only hold data. So before writing anything, we decide: what is the data version of this thing?

10:15. No code on screen for this whole section. Something happens in the world: a person taps a key, drags a finger across the keyboard. A program can't hold "a person tapping". It can only hold numbers, strings, lists. So the real first job of a programmer is deciding what the data version of a thing is. That decision is a choice, and different choices decide which questions you can answer at all. Let that sit for a moment before moving on.

We haven't written any code, but we've found the thing worth capturing. That move, plain description first and then spotting the measurable thing inside it, is what we do twice today.

Still no code: these are descriptions of data, not JavaScript. One action, three versions. Click each question in turn. A count answers "how many" and nothing else. The key names answer "which key", but not "how fast". Only the moments can answer "how fast" and "did they speed up". The point: what you store decides which questions you can ever ask later. Where variables live

          
Why is taps at the top?

          
In the tap code, taps sits above the function and gap sits inside it. Where a variable is made decides how long it lasts, and who can see it.

        

        
11:10, about fifteen minutes for this section, before the swipe. These two ideas were moved here from Friday's Objects lecture, and the tap code we just wrote is the reason they matter: one variable has to remember every tap, the other only matters for one tap. Scope first, then destructuring as its first payoff. Timing knock-on: Example 2 is shortened to 11:25–11:40, so the paper activity keeps its fifteen minutes.

      


      
      

        
Where variables live · Why forget?

        

        
Some things you only need briefly

        

          

            
In your head

            
For years: your name, the way home, your friends' faces.

            
For seconds: a door code from a text, held until you've typed it. The 1 you carry when you add 27 + 15.

            
Short-term memory forgets on purpose. If you kept every door code, the one you need would be lost among them.

          

          

            
In code

            
For the whole time: taps, every tap, for as long as the page is open.

            
For a moment: i in a for loop, only while the loop runs. gap in keyDown, only for this one tap.

            
If every i and every gap stayed forever, they would pile up and get in each other's way.

          

        

        
Motivate scope before naming it. Start with people: some things we remember for years, others only for seconds, like a door code someone texted you, or the 1 you carry in 27 + 15. Ask: what's the door code from the last building you visited? Nobody knows, and that's a good thing. Short-term memory forgets on purpose. Code is the same. taps has to last as long as the page. But i in a loop only matters while the loop runs, and gap only matters for one tap; a temporary calculation inside a function is scrap paper. If JavaScript kept every one of them forever, every loop's i would clash with every other loop's i. So variables come with a lifetime, and where you write them decides it. That's what the next two slides show.

Where variables live · Scope

        

        
Scope: where a variable can be seen

        

          

            

              
taps.jsclick a variable

              

            

          

          

            

            
Click a variable to see where it can be used.

            

              
1A variable belongs to the nearest { } around the line that makes it.

              
2It exists from that line to the closing }, then it's gone.

              
3Code inside can see out. Code outside can't see in.

            

          

        

        
Now name it: scope. Each pair of braces makes a box, and boxes sit inside each other: the file, keyDown, the if, the for loop. Click each variable in turn and its lines light up. taps: the whole file, as long as the page. event: only inside keyDown, a new one for every key press. gaps: only inside the if, made fresh each tap. i: only inside the for loop; once the loop ends, i is gone, which is exactly what we want from a loop counter. Read the three rules aloud. Rule 3 explains the ReferenceError from the last slide: console.log(gap) at the bottom of the file is outside, looking in. Act it out if there's time: four students stand in nested hoops or chalk circles on the floor. Each holds the variables of their box. Someone inside may ask anyone in a bigger circle around them for a value; nobody may reach into a smaller circle.

A key doesn't know where it is

        

          

            
To JavaScript, "w" is a string. Nothing about it says "left of e". So we make that up ourselves.

            

              
row.jsindexOf is new

              

            

          

          

            

            

            
We chose this list and its order. The order of the array is what makes "left" and "right" something a program can work out at all.

          

        

        
The key teaching move of Example 2. A key like "w" has no built-in sense of being left of another key. So we make one: we define the row as an array, and a key's position is its index in that array, found with row.indexOf(key). New: indexOf. It gives back the position of the first match, or -1 if the value isn't in the array at all. Click the row and press keys: q is 0, p is 9, and a gives -1. Emphasise: we chose this representation. Put the letters in a different order and "direction" would mean something else.
