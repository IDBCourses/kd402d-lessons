Core · Exercise 3 · block1/taps.js

  
The pattern is in the gaps

  

    

      
3aAfter the push, work out the gap between the newest tap and the one before, and log it:let i = taps.length - 1; let gap = taps[i] - taps[i - 1];

      
3bPredict: slow or quick tapping, which gives the smaller gaps? Check.

      
3cTap once. The first gap logs something odd. What, and why? Fix it, so the first tap logs no gap.

      
3dPredict, then try: move let taps = []; into keyDown. What's in the list after three taps? Move it back. In a comment: why does taps live at the top, and gap inside?

    

    

      
What your console should show

      

      
console

    

  

  
Done whenevery tap after the first logs a gap, the first logs none, and your 3d comment says where taps has to live and why.

  
3c: with one tap, i is 0, so taps[i - 1] is taps[-1], which is undefined, and a number minus undefined is NaN. The fix is if (taps.length > 1) around the gap. 3d is this morning's scope section: inside keyDown, every tap makes a new empty list, so it only ever holds one moment. taps has to remember every tap, so it lives at the top; gap is only about this tap, so it's made inside, fresh each time, and gone when the function ends. Common mistake to watch for: logging a time instead of a gap (numbers like 1760000000000).

P1: swipe[2] and times[2] describe the same key; if one list gets a value the other doesn't, every pair after it is wrong. That's why both pushes sit side by side. Other rules are fine if they can say why.
