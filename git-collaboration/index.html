Why a shared workflow

One repo. Four people. Same file.

Your fork has been yours alone. This afternoon your A1 group gets one repo, and everyone in the group pushes to it.

Until now, each student has had their own fork and nobody else changed it, so pull and push never surprised them. A group repo is different: while you work, someone else changes main. Ask: what could go wrong when two people change the same file at the same time and both push? Take two or three answers, then move to the next slide.

Why a shared workflow · Two people, one line

Both change line 1. Then what?

Ana's laptop · README.mdpushes first
1 # Team RainAna changed the title and pushed to GitHub.
Ben's laptop · README.mdpushes second
1 # Sounds we likeBen changed the same line, before he had Ana's change.
Students answer on their own laptops; then ask the room for a show of hands per option before anyone reveals it. The point: Git never silently throws a commit away. It combines changes to different lines on its own. When two changes touch the same line, it stops and a person decides. That's a merge conflict, and it isn't an error or anyone's fault: it's Git asking a question. (Strictly, GitHub first refuses Ben's push until he pulls; the pull is where the conflict appears.)
Why a shared workflow · Words for today

Six new words

branchA separate line of work. You change things there without touching main.
mainThe branch everyone shares. It must always run.
pull request"Please merge my branch into main." Your group sees the changes first. "PR" for short.
reviewA groupmate checks out your branch, runs it, then approves or asks for changes.
mergeCombine one branch into another. Usually Git does this by itself.
merge conflictTwo branches changed the same lines. Git asks a person to choose.
Last week's words were repository, clone, commit, push, pull and fork. These six build on them. Leave this slide up a moment for people to copy; the demo uses every word on it.

Live demo · Where a conflict happens

Two branches, one line

The same shape as before, but both branches change line 1 of README.md. The first merge is fine. The second can't merge because main's line 1 has changed since that branch started: GitHub shows "This branch has conflicts that must be resolved". The fix happens on the second author's branch, not on main: they pull main into their branch, choose what line 1 should say, commit and push. Then the pull request merges cleanly. This is exactly what students do in round 2.
Live demo · In VS Code

Watch for these six moments

1Make a branch. Click the branch name at the bottom left → Create new branch…
2Commit, then publish. A new branch's first push is the Publish Branch button.
3Open a pull request on github.com: Compare & pull request.
4The second PR conflicts: This branch has conflicts that must be resolved.
5Pull main into the branch, choose a change, commit, push.
6Review it: check out the branch, run it, approve. Then merge.
Bottom left
The name of the branch you're on. Click it to switch branches or make a new one.
Source Control
Commit, Sync Changes and Publish Branch. The ··· menu has Pull, Fetch and Branch.
github.com
Pull requests, reviews and merging all happen on the website.
Do the whole thing live in your demo repo. You need two "people": the easiest way is to make the first change in VS Code on one branch, and the second in github.com's web editor (press . on the repo page, or the pencil icon on README.md) on another branch, so both edit line 1. Merge the first PR on github.com. Then show the second PR's conflict message, go back to VS Code on that branch, and run Git: Pull from… (Command Palette) → origin → origin/main. README.md appears under Merge Changes; resolve it with Accept Current / Accept Incoming above the markers, save, press + to stage, commit, Sync Changes. Back on github.com the PR now says it can merge. Finally review it: in VS Code click the branch name and pick the branch, run or open it, then on github.com Files changed → Review changes → Approve. (You can't approve your own PR; for the demo, say this out loud and merge without approval.) Narrate where you click; students copy this in a few minutes.

The group workflow

  
Seven steps, every time

  

    
1Pull main before you start anything.Click the branch name at the bottom left → main, then Sync Changes.

    
2Make a branch named after the feature: score-display, not anna.Branch name at the bottom left → Create new branch…

    
3Commit and push to your branch. Keep it short-lived: a day or two at most.The first push is Publish Branch; after that, Sync Changes.

    
4Pull main into your branch and resolve any conflicts before you open the PR.Command Palette → Git: Pull from… → origin → origin/main.

    
5Open a pull request on github.com: what changed · how to test it · anything you're unsure about.

    
6A groupmate reviews: checks out your branch, runs it, then approves or requests changes.

    
7You merge, then delete the branch. main must always run.

  

  
10:45–11:00. This is the loop students use in A1, the same steps as the GitHub Workflow page and the group repo's README. Walk it once, pointing back at what they saw in the demo. Why step 4: conflicts get fixed on your own branch, by the person who knows the change best, before anyone reviews it. Why short-lived: the longer a branch lives, the more main moves under it and the bigger the conflicts. A1 only runs a week. Why the author merges: they know when it's ready. The Command Palette is Ctrl+Shift+P (Cmd+Shift+P on a Mac).

Name the feature, not the person

  
A branch name says what the branch is for. Lowercase words with dashes. Keep it, or rename it?

  

  

  
Quick, one minute. A person's name says nothing about what the branch does, and the same person will have several branches. Vague names (my-stuff, fixes) make it hard to review: what am I testing? Spaces aren't allowed in branch names at all; VS Code turns them into dashes.

Round 1: a clean pull request

  

    

      
1Everyone: pull main, then make a branch named after a sound you like: add-rain-sound.

      
2Make a new file, sounds/rain.md. Write one line: the sound and why you like it. Save.

      
3Commit (Add rain sound), then Publish Branch.

      
4On github.com: Compare & pull request. Fill in what changed · how to test it · anything you're unsure about. Create pull request.

      
5Reviewer: Sync Changes, click the branch name, pick origin/add-rain-sound. Open the file and look at it.Then on github.com: Files changed → Review changes → Approve → Submit review.

      
6Author: Merge pull request → Confirm merge → Delete branch. In VS Code, switch back to main and Sync Changes.

    

    

      
Who reviews whom
The person on your left reviews your PR. GitHub won't let you approve your own.

      
Why separate files
Everyone makes a different file, so nothing conflicts in this round. Round 2 is the conflict.

    

  

  
Done wheneveryone's sound is in sounds/ on main, and everyone has reviewed one PR.

  
About 20 minutes. Everyone authors one PR and reviews one. The "run it" here is opening the file (Ctrl+Shift+V / Cmd+Shift+V shows the Markdown preview): there's no code to run yet, but the habit is the same, which is to check out the branch on your own laptop rather than only reading the diff on github.com. Hands-on · Round 2

  
Round 2: a conflict on purpose

  

    

      
1In pairs: both pull main and make a branch named after your idea for the title, e.g. title-team-rain.

      
2Both change line 1 of README.md to a different title. Commit, publish, open a PR.

      
3Review and merge the first PR. The second now says This branch has conflicts that must be resolved.

      
4Second author: Command Palette → Git: Pull from… → origin → origin/main. README.md shows under Merge Changes.

      
5Choose: Accept Current, Incoming, Both, or edit by hand. No markers left. Save, + to stage, Commit, Sync Changes.

      
6The PR updates by itself. Review it, run it, merge it.

    

    

      
Three in your group?
Two of you make the conflict. The third reviews both PRs, then swaps in for the next go.

      
Then swap
Do it again with the other person merging first, so you both resolve a conflict.

    

  

  
Done whenmain has one title, no <<<<<<< in it, and you've each resolved a conflict.

  
About 20 minutes. Make sure both branches start from the same main (step 1 at the same time), or the second person may already have the first title and get no conflict. If someone's conflict doesn't happen, ask: did you pull main after the first PR merged? Then they've seen what step 4 of the workflow is for. Snags: the conflict resolved in github.com's web editor instead (fine, but do the next one in VS Code); markers left in the file and committed (search for <<<<<<<); "Pull from…" pulled the wrong branch; Commit greyed out until the file is staged with +.

Stretch: ask for changes

  

    

      
1Author: open a PR with a small mistake in it on purpose, like a typo in your sound file.

      
2Reviewer: in Files changed, click the + next to the line and write a comment. Then Review changes → Request changes.

      
3Author: fix it on the same branch in VS Code. Commit and Sync Changes.

      
4Reviewer: look again, run it, approve. The author merges.

    

    

      
No new PR
A pull request follows its branch. Push more commits to the branch and the PR updates.

      
Be kind, be specific
"Line 1 says rian, I think you meant rain" helps. "This is wrong" doesn't.

    

  

  
Done whena PR has gone from Changes requested to Approved to merged.

  
For groups that finish both rounds. The new idea: a PR isn't a one-shot thing; it follows the branch, so the conversation and the fixes stay in one place. Students often close the PR and open a new one: stop them. Model the tone of a review comment; in A1 they review each other's work for a week, so this matters.






  
Hands-on · When it goes wrong

  
The three most common snags

  

    
Forgot to pull main
Your branch started from an old main. Pull main into your branch (workflow step 4) and resolve any conflicts there.

    
Committed to main
Not pushed yet? Source Control ··· → Commit → Undo Last Commit. Your changes stay. Make a branch, commit again. Already pushed? Ask a TA.

    
Approved without running
The diff only shows what changed, not what it broke. Check out the branch and run it, every time.

  

  
More problems and fixes: press T.

  
Leave this up during the hands-on part when you're not on a round slide. Always look at the bottom left before committing: if it says main, stop. Committed to main and already pushed: in a practice repo it doesn't matter; tell them so, and in A1 the protection rules on main stop the push.

Troubleshooting T or Esc to close

  

    
Push rejected: "fetch first"Someone pushed to that branch before you. Click Sync Changes: it pulls their commits, then pushes yours.

    
Can't find a groupmate's branchSource Control ··· → Fetch, then click the branch name at the bottom left and pick origin/branch-name.

    
No "Compare & pull request" bannerThe branch isn't on GitHub yet: click Publish Branch. Or open Pull requests → New pull request and pick the branch.

    
"Can't approve your own pull request"Right: a groupmate has to review it.

    
Committed to main by mistakeNot pushed yet: ··· → Commit → Undo Last Commit. Your changes stay; make a branch and commit again.

    
Can't switch branch: "commit your changes or stash them"You have unsaved work on this branch. Commit it first, or discard it if you don't need it.

    
Markers in the file after a mergeDelete every <<<<<<<, ======= and >>>>>>> line, keep the text you want, save, commit.

    
Commit button greyed out after a conflictStage the resolved file first: the + next to it under Merge Changes.

    
404 or "permission denied"You're not in the repo's team yet, or VS Code is signed in to another GitHub account (Accounts icon, bottom left). Ask a TA.

    
The wrong repo is openCheck the Explorer title. File → Open Folder and pick the practice repo, not the exercises fork.
